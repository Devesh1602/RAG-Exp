# PageIndex — Vectorless RAG

## 1. What is Vectorless RAG?

**Vectorless RAG = RAG without embeddings or a vector database.**

Traditional RAG:

```text
Document
   ↓
Chunk
   ↓
Embedding
   ↓
Vector DB
   ↓
Similarity Search
   ↓
Relevant Chunks
   ↓
LLM
```

PageIndex-style Vectorless RAG:

```text
Document / PDF
      ↓
Understand Structure
      ↓
Hierarchical Tree Index
      ↓
LLM Tree Search
      ↓
Relevant Sections
      ↓
LLM
      ↓
Answer + Citations
```

The notebook specifically presents PageIndex as **reasoning-based RAG with no vector DB and no chunking**.

---

# 2. Why Vectorless RAG?

Traditional vector RAG retrieves content based mainly on **semantic similarity**.

```text
Query
  ↓
Embedding
  ↓
Similarity Search
  ↓
Top-K Chunks
```

The problem is:

> **Similarity does not always equal relevance.**

For professional documents such as:

* Annual reports
* Financial documents
* Legal documents
* Research papers
* Technical manuals
* Textbooks

the **document structure itself** can contain important information.

For example:

```text
Annual Report
├── Business Overview
├── Financial Results
├── Risk Factors
├── MD&A
│   ├── Revenue
│   ├── Expenses
│   └── Liquidity
└── Outlook
```

Knowing **where** information belongs can be more useful than simply finding text that is semantically similar.

---

# 3. PageIndex's Main Idea

Instead of creating arbitrary chunks:

```text
PDF
 ↓
500-token chunk
 ↓
500-token chunk
 ↓
500-token chunk
```

PageIndex builds a **hierarchical tree representing the document structure**.

```text
Document
│
├── Introduction
│   └── Background
│
├── Financial Stability
│   ├── Monitoring Vulnerabilities
│   └── International Cooperation
│
└── Conclusion
```

The tree acts like a **smart Table of Contents**.

Each node can contain:

```text
node_id
title
page_index
text / summary
children
```

---

# 4. Why No Chunking?

Traditional RAG might split a document using:

```text
chunk_size = 500
chunk_overlap = 100
```

This can break logical sections.

Example:

```text
Section:
"Revenue increased because of..."

       ↓ arbitrary chunk boundary

"...international demand."
```

The information may become separated.

PageIndex instead tries to preserve the author's structure:

```text
Chapter
   ↓
Section
   ↓
Subsection
   ↓
Paragraph / Content
```

So retrieval happens at the **document-section level** rather than arbitrary token chunks.

# 11. Why Compress the Tree?

A large document could contain hundreds or thousands of nodes.

Sending the entire tree with full text to the LLM would be expensive.

The notebook therefore compresses the tree and sends information such as:

```text
node_id
title
short summary
```

instead of all document content.

```text
Large Tree
   ↓
Compress
   ↓
Titles + Summaries
   ↓
LLM
```

Then only the selected nodes are fetched for detailed context.

This is an important efficiency pattern:

> **Use a lightweight structural representation for search, then retrieve full content only for selected nodes.**

# 14. Complete `vectorless_rag()`

The notebook combines everything into:

```python
vectorless_rag(
    query,
    tree
)
```

Conceptually:

```python
def vectorless_rag(query, tree):

    # 1. Search tree
    result = llm_tree_search(query, tree)

    # 2. Find selected nodes
    nodes = find_nodes_by_ids(
        tree,
        result["node_list"]
    )

    # 3. Generate answer
    answer = generate_answer(
        query,
        nodes
    )

    return answer
```

So the complete pipeline is:

```text
Query
 ↓
LLM Tree Search
 ↓
Node IDs
 ↓
Find Nodes
 ↓
Section Content
 ↓
LLM
 ↓
Cited Answer
```

# 15. Expert-Guided Retrieval

This is one of the most interesting features in the notebook.

You can give the LLM **domain-specific routing rules**.

Example:

```text
If query mentions EBITDA
        ↓
Prioritize MD&A

If query asks about risks
        ↓
Prioritize Risk Factors

If query asks about liquidity
        ↓
Check Cash Flow + Liquidity sections
```

Instead of modifying the embedding model:

```text
Traditional Vector RAG
        ↓
Fine-tune embedding model
```

PageIndex can use:

```text
Domain Knowledge
       ↓
Prompt Rules
       ↓
LLM Tree Search
```

---

# 16. Why Expert Rules Are Powerful

Imagine a financial document.

Question:

```text
"What are the company's profitability risks?"
```

A generic vector search may retrieve:

```text
Market Risk
Economic Risk
Product Risk
Profitability
```

But an expert may know:

```text
Profitability
     ↓
MD&A
     ↓
Specific financial metrics
```

The expert rule tells the LLM where to look.

Therefore:

> **Expert knowledge becomes a retrieval-routing mechanism.**

# 22. Vector RAG vs Vectorless RAG

| Aspect               | Vector RAG                 | PageIndex / Vectorless RAG        |
| -------------------- | -------------------------- | --------------------------------- |
| Document preparation | Chunking                   | Hierarchical tree                 |
| Embeddings           | Required                   | Not required                      |
| Vector DB            | Required                   | Not required                      |
| Retrieval            | Similarity search          | LLM reasoning                     |
| Retrieval unit       | Chunks                     | Document sections/nodes           |
| Structure awareness  | Limited                    | Strong                            |
| Page/section context | May be lost                | Preserved                         |
| Expert routing       | Usually additional logic   | Prompt-based rules                |
| Best fit             | General semantic retrieval | Structured/professional documents |

# 26. Limitations

Vectorless RAG is **not automatically better than vector RAG**.

Potential trade-offs:

### 1. LLM Cost

Tree search requires an LLM to reason over the tree.

```text
Query
 ↓
LLM reasoning
 ↓
Retrieval
```

### 2. Latency

There can be additional reasoning before retrieval.

### 3. Tree Quality

If the document structure is poorly understood, retrieval quality can suffer.

### 4. Large Trees

Very large document trees still need compression or hierarchical search.

### 5. Not Every Dataset Is Hierarchical

For short, unstructured text, vector search may be simpler and cheaper.

# 27. Interview Questions

### Q1. What is Vectorless RAG?

> Vectorless RAG retrieves information without converting documents into embeddings or storing them in a vector database. PageIndex builds a hierarchical document tree and uses an LLM to reason over that structure to select relevant sections.

### Q2. How does PageIndex retrieve documents?

> It gives the LLM a structural representation of the document tree. The LLM reasons about the query and identifies the node IDs containing relevant information.

### Q3. How is this different from vector RAG?

> Vector RAG uses embedding similarity to retrieve chunks, while PageIndex uses LLM reasoning over document structure to identify relevant sections.

### Q4. Why doesn't PageIndex need chunking?

> Instead of arbitrarily splitting documents into fixed-size chunks, PageIndex preserves the document's natural hierarchy and retrieves sections or nodes.

### Q5. What is a node?

> A node represents a retrievable section of the document and can contain an ID, title, page information, summary, and child nodes.

### Q6. Why compress the tree?

> To reduce the number of tokens sent to the LLM. The search phase can use titles and summaries, while the full content is retrieved only for selected nodes.

### Q7. What is expert-guided retrieval?

> It injects domain-specific routing rules into the LLM prompt so the model knows which document sections should be prioritized for particular types of questions.

### Q8. Can PageIndex work without OpenAI?

> The notebook's demonstrated PageIndex workflow uses OpenAI models, while its self-hosted option still uses an OpenAI key for tree generation.

# 28. Most Important Interview Distinction

```text
Vector RAG
──────────
Embed → Similarity Search → Top-K Chunks → LLM


Vectorless RAG
──────────────
Tree → LLM Reasoning → Relevant Sections → LLM
```

### Think of it this way:

**Vector RAG asks:**

> “Which text is mathematically similar to my query?”

**PageIndex asks:**

> “Given the structure of this document, which sections should I inspect to answer this question?”

# 29. Interview-Ready Explanation

> “I worked with PageIndex to understand a vectorless RAG architecture for structured documents. Instead of chunking a PDF and embedding every chunk into a vector database, PageIndex builds a hierarchical tree representing the document's natural structure. At query time, an LLM performs tree search and reasons over section titles and summaries to identify the relevant node IDs. We then retrieve the actual content from those nodes and pass it to another LLM to generate a grounded answer with section and page citations. The approach is especially useful for structured documents such as financial reports, legal documents, research papers, and technical documentation, where understanding the document hierarchy can be more useful than pure semantic similarity.”
