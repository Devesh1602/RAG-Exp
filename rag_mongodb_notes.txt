# RAG with MongoDB Atlas Vector Search

## 1. What is this project?

This notebook implements a **RAG pipeline using MongoDB as the vector database**.

Instead of using FAISS, the document embeddings are stored directly in a MongoDB collection, and MongoDB Atlas Vector Search is used to retrieve semantically similar documents.

```text
Documents
   ↓
OpenAI Embeddings
   ↓
MongoDB Collection
   ↓
MongoDB Vector Search
   ↓
Relevant Documents
   ↓
LLM
   ↓
Answer
```

# 3. Generate Embeddings

The notebook creates an OpenAI client:

```python
from openai import OpenAI

client = OpenAI()

model = "text-embedding-3-large"
```

Then defines:

```python
def get_embedding(text, input_type="document"):
    response = client.embeddings.create(
        model=model,
        input=text
    )

    return response.data[0].embedding
```

### What does this do?

It converts text into a numerical vector.

```text
"MongoDB Vector Search"
          ↓
    Embedding Model
          ↓
[0.021, -0.034, 0.017, ...]
```

These vectors represent the semantic meaning of the text.

# 8. MongoDB `$vectorSearch`

The actual vector search uses MongoDB's aggregation pipeline:

```python
{
    "$vectorSearch": {
        "index": "vector_index",
        "queryVector": query_embedding,
        "path": "embedding",
        "numCandidates": 3072,
        "limit": 5
    }
}
```

### Meaning

```text
queryVector
    ↓
Compare against
    ↓
embedding field
    ↓
Using vector_index
    ↓
Return top 5
```

The notebook uses `numCandidates=3072` and `limit=5`.

---

# 9. `numCandidates` vs `limit`

This is an important interview question.

### `numCandidates`

Number of candidates considered during approximate vector search.

```text
numCandidates = 3072
```

### `limit`

Number of final results returned.

```text
limit = 5
```

Conceptually:

```text
MongoDB Collection
       ↓
Consider ~3072 candidates
       ↓
Similarity ranking
       ↓
Return top 5
```

So:

> **`numCandidates` controls the search candidate pool; `limit` controls how many final documents are returned.**

# 11. Complete Retrieval Function

The notebook defines:

```python
def get_query_results(query):

    query_embedding = get_embedding(
        query,
        input_type="query"
    )

    pipeline = [
        {
            "$vectorSearch": {
                "index": "vector_index",
                "queryVector": query_embedding,
                "path": "embedding",
                "numCandidates": 3072,
                "limit": 5
            }
        },
        {
            "$project": {
                "_id": 0,
                "text": 1
            }
        }
    ]

    results = collection.aggregate(pipeline)

    array_of_results = []

    for doc in results:
        array_of_results.append(doc)

    return array_of_results
```

The function:

1. Embeds the query.
2. Runs MongoDB vector search.
3. Retrieves the top 5 results.
4. Projects only the `text` field.
5. Returns the results as a Python list.

---

# 12. Why `$project`?

The pipeline contains:

```python
"$project": {
    "_id": 0,
    "text": 1
}
```

This controls which fields are returned.

Instead of returning:

```text
_id
text
embedding
other metadata
```

it returns:

```text
text
```

This prevents unnecessarily passing large embedding vectors to the next stage of the application.

# 14. MongoDB RAG vs FAISS RAG

You previously worked with FAISS-based RAG.

### FAISS

```text
Documents
   ↓
Embeddings
   ↓
FAISS
   ↓
Similarity Search
```

### MongoDB

```text
Documents
   ↓
Embeddings
   ↓
MongoDB Collection
   ↓
Atlas Vector Search
```

### Key Difference

| FAISS                                                 | MongoDB                                       |
| ----------------------------------------------------- | --------------------------------------------- |
| Primarily vector index/library                        | Full database                                 |
| In-memory/local commonly used                         | Persistent database                           |
| Vector retrieval                                      | Vector + database capabilities                |
| Good for prototypes                                   | Better suited to database-backed applications |
| Metadata/database operations limited compared with DB | Native document storage + filtering           |

# 19. Interview Questions

### Q1. Why use MongoDB in RAG?

> MongoDB can store application documents, metadata, and embeddings together while providing vector similarity search through MongoDB Atlas Vector Search.

### Q2. What is `$vectorSearch`?

> `$vectorSearch` is the MongoDB aggregation stage used to perform vector similarity search against an indexed embedding field.

### Q3. What is `queryVector`?

> It is the embedding representation of the user's query that MongoDB compares against stored document embeddings.

### Q4. What is `numCandidates`?

> It specifies the number of candidate vectors considered during approximate vector search before selecting the final results.

### Q5. What is `limit`?

> It specifies the number of final documents returned by the vector search.

### Q6. Why use cosine similarity?

> Cosine similarity measures the directional similarity between vectors and is commonly used to compare semantic embeddings.

### Q7. Why create a vector index?

> The vector index allows MongoDB to efficiently perform similarity search over the stored embeddings.

### Q8. What happens during ingestion?

> Documents are converted into embeddings and stored in MongoDB along with their text and potentially metadata.

### Q9. What happens during retrieval?

> The user's query is embedded and passed to `$vectorSearch`, which finds the most semantically similar stored document vectors.
